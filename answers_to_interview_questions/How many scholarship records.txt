  Anticipated follow-ups

  "Why only 96? Why not scrape thousands?"

  ▎ Hackathon scope + cost control. Each source call is an LLM request with web-scraping tool use; at 8 sources × ~10 scholarships × several runs, that's a
  ▎ few hundred tool calls. For an MVP demo I only needed enough variety across countries, degrees, and fields to make matching feel real. The architecture
  ▎ scales horizontally — add sources to FIXED_SOURCES and the same pipeline handles them.

  "Why a fixed list of sources instead of discovering them?"

  ▎ Trust and quality control. LLM-driven source discovery would have produced a lot of noise (blogs, dead listings, affiliate spam). I curated 8 known-good
  ▎  scholarship index pages and let the LLM do the per-page extraction where its value is highest.

  "How do you handle scholarships that disappear from the source?"

  ▎ Honest answer: I don't yet. The upsert adds or updates; it doesn't mark rows stale. The fix is either a last_seen_at column updated on each run and a
  ▎ cleanup job, or a tombstone flag on records that didn't appear in the latest run for a given source.

  "How do you dedupe across runs?"

  ▎ Two layers. (1) The LLM prompt includes an exclusion list of already-known scholarship names (existingNames passed into buildScrapePrompt), so the model
  ▎  is steered away from re-extracting them. (2) The DB enforces uniqueness on the slug id via upsert(..., { onConflict: 'id' }), so even if the LLM
  ▎ ignores the exclusion hint, re-inserts are idempotent.
